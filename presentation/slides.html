One Codebase, Five Locales, Zero Server

The engineering story of a multilingual developer portfolio built for static export — and why the hardest constraint became the best design driver.

Opening — what is it?

The product: a multilingual portfolio

What the user gets

  • 5 locales: EN, FR, AR (RTL), ES, TR
  • Home, About, Projects, Project detail, Contact
  • Dark/light theme with persistence
  • Contact form → email (Resend)

What it must NOT be

  • Not a CMS, not a blog engine
  • Low traffic, one maintainer

Opening — the problem

The Hostinger 403 that shaped everything

LiteSpeed: visiting /en redirects to /en/ — then serves 403 if en/index.html does not exist.

The fix is not a marketing nicety; it is the correctness of every route:

// next.config.ts:9-13
const nextConfig = {
  output:     isStatic ? 'export' : undefined,
  trailingSlash: isStatic ? true : undefined,   // → en/index.html
  images: { unoptimized: isStatic },
};

Rule: directory-based routes only (en/index.html), never en.html. The route proof is a 40-check script, not a feeling.

Thesis

Correct static export
is a constraint, not a limitation

It rewrites routing, rendering, i18n, theming, and the contact pipeline — and the decisions it forces are the project's real engineering.

Decisions — stack

Why Next.js + React here at all?

  • File-based App Router → directory routes map 1:1 to the static-export rule
  • Server Components by default → most pages ship as pre-rendered HTML, near-zero client JS (README:18)
  • generateStaticParams → the project-detail pages are known at build time (5 locales × N projects)
  • next-intl → message catalogs imported directly as JSON in static mode

Honest trade-off: a static portfolio does not need ISR/middleware — and static export explicitly drops them (README:215). We chose the framework for routing + rendering ergonomics, then turned off the parts that need a server.

Decisions — server/client boundary

Props over hooks in client components

Server (default)

  • Reads files, parses Markdown, loads messages
  • Calls setRequestLocale(locale)
  • Passes locale + data as props down

e.g. projects/page.tsx:52-60

Client ("use client")

  • State + interaction only (filter, menu, theme)
  • No useLocale()/useTranslations()
  • Uses next/navigation, not next-intl/navigation

e.g. ProjectsList.tsx:1-21

Does next-intl hooks work in SSR dev mode? Yes. In static export they pull headers() at build → so the layout bypasses the provider entirely in static mode ([locale]/layout.tsx:55-62).

Technical Deep Dive

Routing, rendering, state, data

The 13 minutes the team is here for.

Deep dive — routing

Routing under static export

  • Root group (index) → client redirect to /en/ ((index)/page.tsx:10-12)
  • [locale] layout: lang, dir, setRequestLocale, generateStaticParams ([locale]/layout.tsx:18-53)
  • Dynamic [id] → generateStaticParams enumerates (locale, project) pairs at build
  • Every known URL is a real index.html on disk — the 40-check script proves it

LiteSpeed needs trailingSlash:true; without it, /en → 301 → 403. This is the #1 breaking point (AGENTS.md).

Deep dive — rendering

SSG, not SSR, not CSR

ModeWhere it runsIn this project
SSGBuild time (once)All pages — HTML written to out/
SSREach request (server)Only via pnpm dev / pnpm start — not shipped
CSRBrowser, after loadClient components for interaction only

SSG is why the server needs no runtime and hosting can be cheap static files.

Deep dive — Hydration ①/④

Hydration: what actually happens

1. Server render (build): React renders HTML for each route. It has no browser: window, localStorage, matchMedia do not exist.

// providers.tsx:19-24 — the lazy initializer must be safe on the server
const [theme, setThemeState] = useState<Theme>(() => {
  if (typeof window !== "undefined") {          // guard: no window at build
    return (localStorage.getItem("theme") as Theme) || "system";
  }
  return "system";                              // fixed server-side default
});

The guard is what stops the build from crashing — but it is only half the story (next slide).

Deep dive — Hydration ②/④

HTML first, then React attaches

  • 2. HTML response: the browser renders the static HTML immediately — before any JS finishes.
  • 3. First client render: React must produce the same initial tree the server produced. Any difference is a mismatch.
  • 4. Hydration: attaching React to the existing DOM and wiring up event handlers — not a CSR that starts from an empty page.
// ThemeToggle.tsx:21-29 — before mount, render the SAME icon the server rendered
{mounted ? (theme === "dark" ? <Icon name="sun"/> : <Icon name="moon"/>)
         : <Icon name="moon"/>}   // stable pre-mount = no mismatch

This is why useMounted gating the icon prevents a hydration warning.

Deep dive — Hydration ③/④

The mismatch and the safe pattern

Wrong — read during render

const theme = localStorage.getItem("theme") || "system";
// Server: "system" (no window)     — renders dark
// First client render: "light"     — renders light
// MISMATCH before hydration ⇒ warning / error /
// tree reprocessing / unexpected DOM

Right — read after mount

// 1) fixed default first        (providers.tsx:23)
// 2) read real value after mount (useMounted)
// 3) hydrated guard so the saved value is NOT
//    overwritten by the server default
{mounted ? <Icon name={theme==="dark"?"sun":"moon"}/>
         : <Icon name="moon"/>}

Pattern: fixed default → read after mount → hydrated save-guard.

Deep dive — Hydration ④/④

Effects after commit — and the key distinction

  • 5. Effects after commit: useEffect runs after the tree is committed. It can read browser APIs and then update state in a later, valid render.
  • Key distinction: a mismatch during the first render is a bug; a state update after useEffect is expected — if the first render matched.
// providers.tsx:37-48 — effect applies theme + listens to system changes
useEffect(() => {
  applyTheme(theme);
  const mq = window.matchMedia("(prefers-color-scheme: dark)");
  mq.addEventListener("change", handler);   // only browser, after commit
  return () => mq.removeEventListener("change", handler);
}, [theme]);

suppressHydrationWarning on <html> silences the attribute-level warning (layout.tsx:53) — the pattern still (not) overrides a saved value.

Deep dive — data

Data: content in the repo, no database

  • Content is versioned files: content/{locale}/home.md, projects.json, about.md
  • No CMS, no DB, no ORM — the fallback in getProjectData (English) is the only resilience layer
  • Contact POST → src/api/contact/route.ts → Resend SDK
  • Env: RESEND_API_KEY (optional), CONTACT_EMAIL default fathi733@gmail.com
// api/contact/route.ts:34-58 — if key missing, it logs instead of failing
if (resendApiKey) { /* build + send email */ }
else { console.log("no RESEND_API_KEY", data); }

This route runs only under SSR dev/prod. In the static export there is no server to handle it — a known limit (see Trade-offs).

Deep dive — performance

Performance: static by design

  • Pre-rendered HTML — nothing to compute per request
  • Images unoptimized at export (next.config.ts:11-13); project covers are pre-converted WebP (git log)
  • .htaccess caching + gzip on LiteSpeed (out/.htaccess:15-36)
  • No service worker / PWA — honest limitation for this scope

Trade-off: static export drops ISR and Image Optimization (README:215). Fast, but not dynamic.

Deep dive — security

Security: small surface, deliberate

  • No auth / no tokens — there is no server, so no session or secret stored client-side
  • XSS: react-markdown escapes raw HTML by default; no dangerouslySetInnerHTML
  • Contact input: escapeHtml() on name/email/message before injecting into email HTML (api/contact/route.ts:44-48)
  • Spam: honeypot field hidden from humans, flagged by bots (useContactForm.ts:24-28, ContactForm.tsx:20-28)
  • Secrets: RESEND_API_KEY only ever in server env, never bundled

Threat model is honest: the static site has almost nothing to attack; the contact route is the only server surface.

Trade-offs

What we gained vs what we paid

Gained

  • Cheap hosting (static files on shared hosting)
  • Near-instant load, no server to manage/scale
  • 5 locales from one codebase
  • Content versioned in git, no CMS lock-in

Paid

  • No dynamic data, no ISR, no middleware
  • Contact form needs a running SSR server to actually email
  • No auth, no admin, no comments
  • No PWA/service worker
  • No unit tests today

Recognizing what is not solved is the strongest evidence of understanding.

Roadmap

Priorities by risk, not wishes

  1. Unit test net (highest risk) — hooks + content fallback + validation are untested
  2. Contact route strategy — decide SSR deploy (Vercel) vs external form service for actual email
  3. Add next-themes or keep custom? — dedupe the unused dependency listed in package.json
  4. Optional PWA — only if offline value is needed

Order follows the blast radius of being wrong, not the novelty of the feature.

Closing

The best constraint is the one you choose

Static export forced the exact decisions — routing, hydration-safe theming, prop-driven i18n — that make this codebase small, fast, and easy to reason about.
